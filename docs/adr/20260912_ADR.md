# 2026-09-12 ADR

## ADR-20260912-001：升级 Harness 工程层并迁移 Agent Policy schema v3

- 日期：2026-09-12；状态：Accepted；确认人：`arden`。
- 关联需求：使用新版模板升级当前终端项目，并确认采用新版 Agent Policy。`change_id = HARNESS-UPGRADE-202609111732-POLICY-SCHEMA3`；版本门禁分类为 `maintenance`，`required_version = 0.1.0`，不提升产品版本。
- 背景：当前项目由较早 Harness 初始化，尚无 `.harness/upstream-lock.json`，因此无法推断三方共同祖先。已验证的新来源是 Harness 版本 `202609111732`、源码提交 `446b654bbea580237cc8ad31f22a42594a4848c3`。新版删除旧 Task 标题与 SemVer 下位分量 `100` 的兼容层，并把 Agent Policy 升级为 schema v3。
- 决定：先以独立、已渲染候选逐项审计受管、条件和混合所有权文件，使目标与候选在字节及普通权限模式上收敛，再通过 `$desktop-upgrade-harness` 记录首份 bootstrap 基线。升级只更新 Harness 工程层，不覆盖产品代码、产品身份、GUI profile、许可证、产品记忆、Cargo 当前版本或受保护版本周期状态。
- 迁移前策略：`schema_version: 1`；`superpowers: disabled`、`parallel_worktree_subagents: enabled`、`milestone_smoke: enabled`、`milestone_e2e: disabled`，尚无 `user_owned_tasks`；`decision_mode: reuse_then_infer_then_ask`。确认元数据原为 `confirmed_by: arden`、`confirmed_at: 2026-09-10`。
- 策略决定：`docs/AGENT_POLICY.md` 一次性物化为 `schema_version: 3`，并采用 `user_owned_tasks: disabled`、`superpowers: disabled`、`parallel_worktree_subagents: enabled`、`acceptance_smoke: enabled`、`e2e_hint: disabled`；保留 `decision_mode: reuse_then_infer_then_ask`。旧字段 `milestone_smoke`、`milestone_e2e` 与旧 schema 不再兼容或推断。
- Task 影响：普通请求继续在当前 Task 完成，不自动创建左侧 Task；用户仍可明确要求创建。用户可见 Task 唯一使用 `Task {序号} | {当前进度} | {单一结果}`，序号只从同宿主同项目当前与归档的现行合规标题计算；旧四字段标题不再计入。内部 plan、Subagent 和 Worktree 不使用该标题合同，也不占序号。
- 版本影响：Minor/Patch 固定为 `0..99`；Cargo、`.harness/version-state.json` 或发布日志中出现下位分量 `100` 时立即失败关闭，不再延迟规范化。本项目当前 Cargo 与状态目标均为 `0.1.0`，不存在需要迁移的 `100` 数据。
- 理由与风险：建立真实上游锁后，后续升级可以进行可审计的三方比较；schema v3 让 Task、冒烟和 E2E 偏好语义明确。风险是旧标题不参与未来序号计算，以及未来引入 `*.100.*` 数据会被拒绝；这是新版明确的失败关闭行为，已在本次确认中接受。
- 验证：要求来源 Git HEAD/工作区与声明版本一致且 Harness 硬门禁通过；候选不得包含受保护或墓碑路径、冲突标记、符号链接或特殊文件；目标与候选收敛后记录 bootstrap 锁，并运行版本门禁、发布日志与并行 Worktree helper 的相关非空回归。产品构建、GUI 冒烟、E2E 和完整验收不属于本次工程升级。
- 恢复或调整标准：若真实使用证明新 Task 合同、严格版本边界或任一持久策略不可接受，必须由负责人明确确认新的目标值并写入后续 ADR；不得静默恢复旧 schema、旧字段名、旧标题兼容或 `100` 兼容读取。工程文件可依据已记录的上游基线进行后续三方升级或人工回退，但受保护产品事实仍须独立决定。

## ADR-20260912-002：首版采用本地 Grid、固定内容 SOP 与可插拔 AI

- 日期：2026-09-12；状态：Accepted；确认人：`arden`。
- 关联需求：实现已确认的飞书式批量内容工作台设计。`change_id = FEATURE-BATCH-AI-CONTENT-WORKBENCH-MVP`；版本门禁计划为 `required_version = 0.2.0`。
- 背景：现有项目只是中性 Tauri/React/Rust scaffold，尚无产品领域、持久化或 AI 能力。用户需要一次录入几十个标题、按行执行内容 SOP，并在可管理的 Grid 中查看、重试和审核结果，以替代飞书 AI 的调用限制。
- 决定：首版产品以本地持久化 Grid 为权威工作区，固定执行“正文 → 简介 → 配图 → Markdown/HTML → 审核”SOP；任务状态、依赖、版本、幂等、重试和批准保护全部进入 Rust core。Tauri 适配器使用本地 SQLite/SeaORM 提供原子持久化，并提供 OpenAI-compatible 文本和图片 Provider；非秘密配置持久化，凭据进入系统凭据库。GUI 保留既有 80px compact 侧栏和宿主支持页。
- 外部边界：添加、编辑和预览不发出 AI 请求；只有用户明确测试连接、运行、重试或重新生成才允许调用选定 Provider。自定义 Provider 地址是用户录入的受信任本地配置，允许其自托管 HTTPS 服务；它不接收文章、AI 响应、深链接或其他不受信字符串，界面明确提示密钥与内容会发往该地址。未配置 Provider 时返回稳定错误并保持零出站。测试替身只能由测试构建显式启用，正式 UI 不得把替身显示成真实 AI。
- 数据保护：文章包按版本追加保存，已批准版本不可变；正文编辑使其实际依赖产物过期。API 密钥、认证头和原始未脱敏响应不得进入 SQLite、日志、截图、普通错误或可复制文本。
- 明确排除：飞书 OpenAPI/回写、平台自动发布、通用表格/公式/工作流、云端协作和开放式格式设计器均不在 MVP。
- 理由：固定 SOP 足以完成用户当前闭环，Grid 保留批量操作效率；core-first 和本地事务存储使 GUI、后续 CLI 或未来数据源不会复制业务规则；OpenAI-compatible 契约覆盖多个 AI 服务而不在 core 绑定厂商。
- 风险：真实 Provider 的能力与响应差异可能超出兼容契约，系统凭据库在不同宿主的可用性也需真实验证。允许用户明确选择私有/内部 HTTPS 服务意味着该字段不是面向不受信输入的通用 URL 抓取器；未来如引入远程导入、共享配置或任何非用户直接录入来源，必须先增加独立的地址策略与 DNS/连接级防护。适配器必须把不兼容响应映射为稳定错误，真实联网冒烟保持显式 opt-in，不能用测试夹具替代供应商验证。
- 恢复或调整标准：若固定 SOP 无法覆盖首要场景，再以新 Product Spec/ADR 评估额外固定步骤或受限编排；若 OpenAI-compatible 路径无法覆盖选定厂商，新增窄适配器而不修改领域状态机；飞书同步只有在字段映射、冲突和回写边界单独获批后进入范围。
